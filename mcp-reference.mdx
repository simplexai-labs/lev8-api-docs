The lev8 MCP endpoint exposes Entity Search, Contact Search, and credit balance as typed tools for AI clients.

It uses **Streamable HTTP**, the remote MCP transport: your client sends tool calls over HTTPS to one hosted URL and receives JSON responses. There is no local MCP process, executable, or package to install.

```text
https://api.lev8.com/mcp
```

Every Tool call goes through the public lev8 API, so API-key scopes, task ownership, concurrency limits, idempotency handling, and credit billing still apply.

## Prerequisites

- An active External API Token created from [API Tokens](https://app.lev8.com/api-tokens).
- The Tool scopes required for the operations you want to call.
- An MCP client that supports remote Streamable HTTP and Bearer authentication.

## Configure Codex

Store the Token in the `LEV8_API_KEY` environment variable, then register the hosted endpoint:

```bash
export LEV8_API_KEY="lev8_live_..."

codex mcp add lev8 \
  --url https://api.lev8.com/mcp \
  --bearer-token-env-var LEV8_API_KEY
```

The value above is a placeholder. Use the complete Token shown once by lev8, and never commit it to source control or place it directly in the command.

Your MCP client sends the Token on each request as:

```http
Authorization: Bearer lev8_live_...
```

The Token is request-scoped. It is not a Tool input and does not appear in Tool schemas or results.

## Tools

| Tool | Inputs | Behavior |
| --- | --- | --- |
| `entity_search_create` | `entity_type`, `objective`, optional `limit`, `enable_web_search`, `enrich_fields`, `dedup_lev8_leads`, and `dedup_custom_leads` | Creates a billed asynchronous task. |
| `entity_search_status` | `leads_search_id` | Reads progress. A terminal call can advance billing settlement. |
| `entity_search_fetch` | `leads_search_id`, optional `pts` and `num` | Reads one positional page of available entities. |
| `contact_search` | `contact_type`, `objective` | Finds an email or phone. Only a non-empty result is charged. |
| `credit_balance` | None | Reads the available credits for the Token's billing account. |

`entity_search_create` defaults `limit` to `20`. `entity_search_fetch` defaults `pts` to `0` and `num` to `5`, with a maximum `num` of `500`.

## Entity Search workflow

<Steps>
  <Step title="Create">
    Call `entity_search_create` and save `leads_search_id` from the structured result.
  </Step>
  <Step title="Monitor">
    Call `entity_search_status` until the state becomes `done` or `error`. You can begin fetching as soon as `ready_count` is positive.
  </Step>
  <Step title="Fetch">
    Call `entity_search_fetch`. Advance `pts` by the returned `count` until all `ready_count` results have been read.
  </Step>
</Steps>

A terminal `error` can still have ready results. Fetch them before closing the task.

## Paid Tool retries

The MCP server generates an internal idempotency key for every `entity_search_create` and `contact_search` Tool call. That key is not exposed as a Tool input.

The first release does not automatically retry paid POST operations. Calling the Tool again creates a new key and is treated as a new billable operation, so do not blindly repeat a call whose outcome is unknown.

## Transport and authentication boundaries

- The endpoint is stateless and returns each MCP response as JSON. It does not create a persistent client session or send server-initiated notifications.
- MCP requests use `POST` with JSON bodies; the hosted endpoint does not expose a separate SSE notification stream.
- Authentication uses the existing `lev8_live_...` External API Token as a Bearer credential.
- OAuth, dynamic client registration, browser authorization, and persistent sessions are not supported in the first release.
- The MCP endpoint does not provide Token creation, listing, or revocation Tools.
- Objective text, results, contact details, Tokens, and complete request or response bodies are not written to MCP logs.
- HTTP and upstream failures are mapped to stable Tool errors without exposing internal response bodies.
